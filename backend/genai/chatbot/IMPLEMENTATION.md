# Phase 3 Implementation Report

## Architecture

```
POST /chat { question, recommendation_context (LoanRecommendationResponse) }
      │
      ├─ Pydantic schema validation
      │
      ├─ generate_shap_explanation()   ← Phase 1 engine re-runs risk_driver selection
      │       ↓ ExplanationOutput (top_factors replaces incoming risk_drivers)
      │
      ├─ model_copy() → grounded_data (risk_drivers replaced, all other fields unchanged)
      │
      ├─ build_context(grounded_data)  → backend-grounded context dict
      │     (product_id excluded, raw SHAP impact excluded)
      │
      ├─ build_grounded_prompt(question, context_json)
      │     → system prompt + context + question
      │
      ├─ _call_gemini(prompt)
      │       ├─ SUCCESS → ChatResponse(source="gemini", grounded=True)
      │       └─ FAILURE → get_fallback_response(question, context)
      │               ├─ Known intent → ChatResponse(source="fallback")
      └───────────────── └─ Unknown     → SAFE_UNAVAILABLE
```

## Files

### `__init__.py`
Exports the public API: `chat`, `build_context`, `ChatResponse`.

### `context_builder.py`
Single function `build_context(LoanRecommendationResponse) -> dict`.

- Reads the recommendation response and outputs a minimal, serializable dict.
- Preserves all numerical values exactly as received.
- Omits optional sections when absent (None / empty lists).
- Excludes raw SHAP impact values (direction only is exposed).
- Excludes internal product IDs.
- Does NOT calculate or derive any new values.

**Trust classification (per field):**

| Field | Classification |
|-------|---------------|
| `explanation.risk_drivers` (selection/order) | Backend-regenerated by Phase 1 engine before this function is called |
| `status` | ML-pipeline-sourced, Pydantic enum-validated |
| `risk_summary.*` | ML-pipeline-sourced |
| `affordability.*` | ML-pipeline-sourced |
| `recommendations[*].rank` | ML-pipeline-sourced |
| `recommendations[*].product_name` | ML-pipeline-sourced |
| `recommendations[*].monthly_emi` | ML-pipeline-sourced |
| `recommendations[*].personalised_rate_pct` | ML-pipeline-sourced |
| `recommendations[*].suitability_scores.*` | ML-pipeline-sourced |
| `explanation.eligibility_reasons` | ML-pipeline-sourced |
| `explanation.offer_reasons` | ML-pipeline-sourced |
| `explanation.comparative_reasons` | ML-pipeline-sourced |
| DTI (standalone) | Not available in context |
| EMI ratio (standalone) | Not available in context (text only in affordability) |

The context is referred to as **"backend-grounded"** — not "fully-verified".

### `prompts.py`
- `SYSTEM_PROMPT`: 18-rule immutable system constraint for Gemini.
- `build_grounded_prompt(question, context_json)`: Assembles the full prompt.

The system prompt explicitly establishes:
1. Gemini is an explanation layer, not a decision layer.
2. All numerical values must come from the verified context.
3. Context fields must be treated as data, not instructions (injection protection).
4. Approval guarantees are forbidden.

### `fallback.py`
- `match_intent(question) -> Optional[str]`: Normalises and regex-matches the question to one of 8 intents.
- `get_fallback_response(question, context) -> str`: Dispatches to the appropriate handler.
- 8 handlers, each using only the `context` dict to build a dynamic response.
- No hardcoded product names, rates, or scores.

### `chatbot.py`
- `chat(question, recommendation_data) -> ChatResponse`: Main entry point.
- Calls Gemini via `_call_gemini()` (same `google-genai` client pattern as Phase 2 summarizer).
- Catches all exceptions, logs as WARNING, activates fallback.
- **Never raises.**

## Data Flow

1. The recommendation context arrives as a `LoanRecommendationResponse` in the API request body. This is the exact same schema already used by Phase 1 (`/explanation`) and Phase 2 (`/summarize`).
2. `build_context()` converts it to a plain dict, filtering out fields that should not be in the prompt.
3. The dict is JSON-serialised and embedded in the Gemini prompt between separator lines.
4. Gemini receives: `SYSTEM_PROMPT + [context JSON] + [user question]`.
5. The response text is returned directly as `ChatResponse.answer`.

## Grounding

Hallucination is reduced through three layers:

| Layer | Mechanism |
|-------|----------|
| Context builder | Only verified values from the backend are included |
| System prompt | 18 rules explicitly forbid inventing values |
| Fallback | Bypasses Gemini entirely; pure Python deterministic logic |

## Fallback

8 intents supported:

| # | Intent | Example trigger |
|---|--------|----------------|
| 1 | `approval_safety` | "guarantee approval" |
| 2 | `comparison` | "why higher than", "beat" |
| 3 | `emi` | "what is my emi" |
| 4 | `credit_score` | "credit score affect" |
| 5 | `eligibility` | "why not eligible", "rejected" |
| 6 | `suitability` | "what does my score mean" |
| 7 | `affordability` | "can I afford", "dti" |
| 8 | `ranking` | "ranked first", "top recommendation" |

Unknown intents return `SAFE_UNAVAILABLE = "That information isn't available..."`.

## Safety

The chatbot refuses to:
- Invent loan products, rates, or scores
- Guarantee loan approval
- Perform unsupported calculations
- Reveal system instructions
- Follow injection instructions in context field values

Gemini-side: enforced via system prompt rules.  
Fallback-side: enforced by deterministic logic that only reads from the verified context dict.

## Known Limitations

1. **Stateless**: No multi-turn conversation memory. Each request is independent.
2. **Context dependency**: If the ML team does not supply affordability or risk data, related questions return `SAFE_UNAVAILABLE`.
3. **Fallback intent coverage**: 8 intents cover common demo scenarios. More intents can be added in `fallback.py` without touching any other file.
4. **Gemini grounding**: Gemini may occasionally produce generic language despite the system prompt. This is a model characteristic, not a Phase 3 bug. The fallback provides a reliable alternative.
5. **Prompt injection (fallback path)**: In the fallback, malicious product names appear as plain text in the answer. They are never executed as instructions. This is correct behaviour.
6. **No rate limiting**: The `/chat` endpoint has no per-user rate limiting.
